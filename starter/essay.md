# Reflection

One design decision I made was separating tools by execution boundary rather than by feature: Gateway-routed tools (order tracking, refunds) hit external Lambda functions through MCP, while everything needing tighter control — knowledge base search, loyalty math, browsing — ran as in-process Strands tools or dedicated AgentCore services (Code Interpreter, Browser). This kept business logic that touches money (the loyalty discount calculation) inside a sandboxed, auditable execution path rather than trusting the model's own arithmetic, and it kept the agent's tool list declarative: Gateway tools are loaded dynamically at invoke time via `MCPClient`, so adding a new backend capability later means registering it at the Gateway, not redeploying the agent.

The biggest challenge was environment drift, not agent logic. AWS deprecated the Python `bedrock-agentcore-starter-toolkit` CLI mid-course in favor of a new npm-based `@aws/agentcore` CLI, and both install a binary named `agentcore`. My PATH resolved to the wrong one, so `agentcore configure` failed with an unrecognized-command error that had nothing to do with my code. Once I forced execution through `uv run` inside the correct virtualenv, configuration worked. A second, subtler failure came after deployment: `agentcore invoke` returned "Runtime initialization time exceeded" with no obvious cause. The CloudWatch logs showed `argparse: error: the following arguments are required: payload` — I'd left the file's `__main__` block set to local CLI testing (`main()`) instead of `app.run()`, so the deployed container tried to parse a CLI argument that was never passed and exited before the server ever started. The fix was one line, but finding it required going straight to the runtime logs rather than guessing from the invoke error alone.

For production, I'd add three things before trusting this with real customers. First, a pre-deploy check (CI step or pre-commit hook) that fails the build if `app.run()` isn't active — the exact bug above is easy to reintroduce. Second, per-Lambda least-privilege IAM roles instead of broad execution roles, since refund processing should never share permissions with read-only order lookups. Third, cost monitoring on OpenSearch Serverless behind the Knowledge Base, since unlike Runtime's pay-per-active-second billing, OCU-backed vector stores can carry a baseline cost even when idle.
